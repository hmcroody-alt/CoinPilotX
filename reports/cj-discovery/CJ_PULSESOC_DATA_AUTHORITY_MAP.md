# CJ / PulseSoc data authority map

Discovery date: 2026-09-07. Status: proposed binding boundaries for a future Supplier Gateway, grounded in current CJ documentation and the local commerce code. No CJ adapter, tables, credentials, checkout, UI, or production changes were implemented. Names such as `supplier_inventory_snapshot` below describe a proposed normalized domain; they do not claim those tables exist.

## Existing canonical commerce boundary

Business OS already exposes a thin order facade over the canonical Marketplace order/refund engine. [services/business_os/orders/service.py:1](/Users/hmcherie/Desktop/CoinPilotX/services/business_os/orders/service.py:1) explicitly states that it owns no separate order table or ledger; it re-exports statuses/transitions and delegates creation, payment, fulfillment, cancellation, refunds and disputes. The future Supplier Gateway must serve this canonical domain, with provider records attached as external fulfillment references. A second CJ-specific customer-order or payment engine would violate this existing boundary.

Current merchant products have PulseSoc `product_id`, `seller_user_id`, title, description, retail `price_cents`, currency, inventory, fulfillment type and publication lifecycle. Creation yields a draft; publication is a separate action. [Product creation](/Users/hmcherie/Desktop/CoinPilotX/services/business_os/marketplace/service.py:268), [owned product edits](/Users/hmcherie/Desktop/CoinPilotX/services/business_os/marketplace/service.py:338).

The canonical order engine snapshots the selected merchant product's price, line items, fees, shipping/tax fields and policy versions; it obtains buyer/seller identity from the domain context. [Order creation](/Users/hmcherie/Desktop/CoinPilotX/services/business_os/marketplace/orders.py:193). This is evidence for reuse, not a claim that the existing engine already supports supplier orders, multi-provider carts, all tax jurisdictions, or all required dropshipping flows.

## Authority and reconciliation matrix

| Data or decision | Authority | CJ representation stored by PulseSoc | Merchant override / reconciliation rule |
| --- | --- | --- | --- |
| Merchant account and store | PulseSoc | Optional bound external CJ account/shop reference | Store ownership and role permissions come from authenticated PulseSoc membership. CJ shop existence never grants PulseSoc store access. |
| Merchant storefront product ID | PulseSoc | Link to source `provider_product_id` | Generate and preserve an independent PulseSoc product ID. Multiple merchants may import one CJ product without sharing merchandising state. |
| Storefront title, description, category and SEO | PulseSoc merchant, within platform rules | Supplier source title/description/category in snapshot | Initial import may seed a draft. Refresh supplier snapshot independently; preserve approved merchant edits. Offer a source diff for review instead of silently overwriting them. |
| Product publication, moderation, visibility and channels | PulseSoc | CJ `saleStatus`, `status`, visibility/authority flags | CJ on-sale does not publish a local draft. CJ off-sale/deletion/permission loss removes fulfillment eligibility and can pause availability under PulseSoc policy; it does not erase the local product or order history. |
| Retail price, discounts, markup, retail currency | PulseSoc merchant/pricing policy | CJ cost/discount/suggested retail price observations | Upstream suggested retail is advisory. A CJ cost change cannot alter a placed customer order or increase a customer's charge. New retail price changes require merchant policy/authorization and are versioned. |
| Supplier cost | CJ for CJ's quoted/charged amount | Decimal amount, currency, scope, variant, quote time and source endpoint | Merchant cannot edit CJ cost as if CJ reported it. Separate merchant margin assumptions and currency conversion from observed source cost. A product range is not a selected variant quote. |
| Currency conversion and retail rounding | PulseSoc pricing policy using its chosen validated rate source | Original CJ currency/amount plus conversion rate/time if conversion occurs | Preserve original currency and precision. No implicit assumption that every CJ integer is cents: private inventory `unitPrice` scale remains undocumented. |
| Variant identity and source SKU | CJ | String `pid`, `vid`, `variantSku`, `barcode/barcode2` | Never replace local variant ID with CJ vid. Keep provider identifiers immutable as observed; explicit remapping must record previous identity and cannot mutate historic order lines. |
| Merchant SKU, option labels and display order | PulseSoc merchant | Original source SKU, option dimensions/values | Merchant may change presentation/local SKU, but the fulfillment mapping must still select the correct source variant. Renaming “Blue” cannot point silently to another vid. |
| Physical variant specifications | CJ source observation; PulseSoc owns storefront representation and claims | Weight, dimensions, materials, logistics attributes, HS/customs metadata | Preserve supplier values/units for freight. Store reviewed display overrides separately; flag contradictory or missing safety-critical specifications. No certification flag alone creates a compliance conclusion. |
| Product images, video and size charts | Rights holder; PulseSoc controls licensed display | Source URLs, copyright/purchase state and source snapshot | Import/republication waits for established rights and product approval. Merchant replacement media stays local. Do not infer rights from access to a URL or CJ `isFree` alone. |
| CJ product reviews | Source review author/platform rights; CJ supplies observations | Separate supplier review records with CJ IDs/source labels if approved | Never merge into PulseSoc verified-purchase ratings. License/provenance and publication permission are unresolved. Imported review text/photos are not the merchant's customer records. |
| PulseSoc purchase reviews | PulseSoc canonical review domain | No CJ review as substitute | Existing reviews require an owned completed order containing the product. Supplier reviews cannot satisfy that contract. |
| CJ public / supplier inventory | CJ | `supplier_inventory_snapshot` keyed by connection, source variant, country/warehouse/subwarehouse and inventory type | Merchant may set a safety buffer or selling cap but cannot increase observed CJ stock as a factual supplier observation. Keep factory stock and verified/unverified quantities separate. |
| Merchant-owned CJ private inventory | CJ account's private inventory records | Separate private stock observations: available, transit, locked, used, dispute, frozen; source stock-order refs | Account connection scope is mandatory. Available quantity is distinct from total/in-transit; do not add unrelated state buckets into sellable stock. |
| Merchant-owned local inventory | PulseSoc inventory domain | No CJ authority unless physically placed in CJ private storage | A CJ stock update cannot decrement or replenish the merchant's independent local warehouse. Fulfillment routing selects the source explicitly. |
| Storefront availability / sellable quantity | PulseSoc availability policy | Inputs from scoped source inventory, reservations, merchant limits and freshness | Suggested future rule: derive availability from selected source observations and local commitments, with a conservative stale-data policy. Do not claim an atomic CJ reservation exists; none was found in stock query documentation. |
| Warehouse area, country and physical subwarehouse | CJ | Area ID, country code, storage/stock ID, provider descriptions | Business OS shows useful origin/country and selectable eligible warehouses. Preserve identifier distinctions. Buyers see relevant origin/delivery information rather than provider operational IDs. |
| Supplier shipping method/cost/estimate/restrictions | CJ quotation/logistics service | Provider method/channel and quote tied to destination, quantity, origin, variant and time | Merchant shipping policy may subsidize/mark up customer shipping independently. Supplier quote is not a guarantee of all duties/taxes or final fulfillment cost. |
| Customer shipping charge and checkout promise | PulseSoc merchant checkout policy | Traceable source quote and selected route | Retail shipping charge may differ from supplier cost. Changes in supplier freight after customer payment require an exception process; never auto-charge the difference. |
| Customer identity and relationship | PulseSoc / merchant store | Minimum recipient/address/contact data necessary for authorized fulfillment | CJ recipient records cannot overwrite customer identity, account membership, marketing consent or customer profile. Customer updates do not rewrite already dispatched shipment facts. |
| Customer order and customer order ID | PulseSoc canonical order domain | One or more supplier fulfillment children/external references | CJ order IDs are external fulfillment references. A split/multi-provider fulfillment cannot create duplicate customer orders. |
| Checkout totals, tax amounts, discounts, fees and policy snapshots | PulseSoc canonical pricing/order policy | Supplier cost/tax/charge observations where documented | Provider totals inform supplier cost accounting. They cannot overwrite retail order totals, tax computation, buyer service fees, or the accepted checkout snapshot. |
| Customer payment, capture, refund and payout relationship | PulseSoc canonical payments/order/refund domain and its payment processor records | Supplier payment references kept separately | A CJ PAID notification proves only a supplier order funding fact. It must not mark the customer as paid, capture funds, authorize a refund, or release merchant payout. |
| Supplier order funding and CJ account balance | The connected CJ account's funder and CJ payment records | Supplier funding intent/state/amount/currency/external payment refs | Merchant-owned connection should use authorized merchant funding. A central account requires an explicit funded commercial model; no automatic PulseSoc advance or customer-payment diversion is authorized by this discovery. |
| CJ order ID and supplier order/fulfillment state | CJ | External fulfillment record with raw CJ state + normalized supplier state | Source events update supplier state through validated mapping; unknown/regressive states are reconciled. They are not direct writes to canonical customer-order status. |
| Canonical customer-order status | PulseSoc canonical state machine | Supplier fulfillment state is an input/event | The domain assesses all lines, shipments, captures, refunds and policy before applying a legal local transition. CJ completion alone cannot complete an unpaid or partly fulfilled customer order. |
| Shipment IDs, carrier/channel, tracking number and carrier events | CJ/carrier for provider observations; PulseSoc shipment domain for aggregation | Source shipment/tracking refs/events, timestamps and provenance | Separate shipment facts from order state. Preserve old tracking references on replacement/split; events cannot silently transfer a shipment between merchants/orders. |
| Buyer tracking view and communications | PulseSoc | Sanitized normalized timeline with provider attribution where useful | Route authenticated buyer access through the canonical customer order. Unknown carrier events remain pending/unknown, not invented delivered states. |
| Customer return request / policy / refund status | PulseSoc merchant and canonical return/refund domain | Optional link to supplier recovery case | Customer return/refund decisions follow local policy and payment authority; never wait for an unrelated CJ recovery result unless the approved policy requires that dependency. |
| CJ dispute / return-to-supplier / reimbursement state | CJ supplier recovery workflow | Independent `supplier_recovery_status`, external dispute refs/evidence and amounts | A CJ refund must not automatically refund the customer twice. Supplier reimbursement and customer refund are separate accounting events, potentially with different amounts/timing. |
| Merchant analytics and profitability | PulseSoc | Supplier costs, funding, fulfillment and recovery observations | Compute local retail revenue and net supplier costs from separately reconciled sources. CJ listing counts/supplier orders are not PulseSoc sales counts or merchant revenue. |
| Access control, API credentials and webhook subscriptions | PulseSoc authorization/secret-management boundary; CJ verifies credential entitlement | Protected connection metadata and scoped subscription state | Browser/mobile never receive CJ credentials or raw signed payloads. Source event IDs, openId or shopId alone cannot select/authorize an arbitrary tenant. |

## Proposed identifiers and tenant boundaries

These are design requirements for a future normalized contract, not migration instructions:

| Local normalized reference | Meaning and required scope |
| --- | --- |
| `merchant_id`, `store_id` | PulseSoc authenticated business/store ownership. Current inspected product/order code uses `seller_user_id`; do not claim a new tenant/store identifier already exists without checking the canonical business identity domain. |
| `supplier_connection_id` | PulseSoc-controlled binding of one credential/account relationship to authorized merchant/store scope. Include provider and external account fingerprint; secret values live outside commerce rows. |
| `provider='cj'`, `provider_account_ref` | Provider namespace and protected account identity. CJ openId doubles as signing-secret material, so it is not a public account label. |
| `provider_product_id`, `provider_variant_id`, `provider_sku` | Exact observed CJ identifiers, stored as strings under their provider/connection context. No accidental collision with local product/variant IDs. |
| `merchant_product_id`, `merchant_variant_id` | Independent local sellable product/variant identity linked to a supplier snapshot/reference. Different stores can curate the same source differently. |
| `customer_order_id`, `order_line_id` | Canonical local customer transaction references. Remain valid when supplier changes, cancels, splits, or deletes its product. |
| `fulfillment_id`, `fulfillment_line_id` | Local normalized fulfillment identity. Supports one customer order → several provider orders/shipments and one line split across fulfillment quantities. |
| `provider_order_id`, `provider_order_number`, `provider_payment_id` | Separate external CJ references. Track raw values and their meanings; never infer one is interchangeable with another. |
| `shipment_id`, `provider_shipment_ref`, `tracking_ref` | Local aggregation plus immutable external lineage. Tracking is not globally unique enough to authorize lookup. |
| `customer_refund_id`, `supplier_dispute_id` | Different references with explicit linkage for customer refund vs supplier recovery reconciliation. |
| `provider_event_id` | Deduplication key scoped to connection/provider; preserve received time and processing outcome. CJ `messageId` is not a customer-order authority. |

Every supplier read, refresh job, quote, order command and callback must resolve `supplier_connection_id` from a trusted local binding and verify the linked merchant/store/order ownership. Do not accept body-provided connection, shop, buyer, seller or external order identifiers as sufficient authorization. A shared public catalog cache may contain only content proven public; account prices, private products, My Product membership, private inventory, addresses, payment state and raw callbacks must remain connection-scoped.

The existing [Business OS facade contract](/Users/hmcherie/Desktop/CoinPilotX/services/business_os/orders/service.py:9) states authenticated buyer/seller identity and ownership-scoped reads. Future supplier scopes must extend that canonical boundary rather than create a bypass.

## Proposed refresh and conflict handling

1. Receive and validate a CJ callback against the connection's saved `openId`; deduplicate by connection/messageId. Persist a minimal redacted event envelope and enqueue work before acknowledging within CJ's 3-second deadline. Raw payload retention, if necessary, requires protected access because openId is secret material. [CJ signature contract](https://developers.cjdropshipping.com/en/api/start/webhook.html#_2-signature-authentication).
2. For subscribed products, refresh the supplier snapshot when product, variant or stock changes. STOCK's documented example has `storageNum` and no version/freshness guarantee; verify current inventory through REST instead of assuming a reliable ordered delta stream. [Stock payload](https://developers.cjdropshipping.com/en/api/start/webhook.html#stock-message).
3. Reconcile imported products and active fulfillments on a bounded schedule, with per-connection point/QPS budgeting and jobs deduplicated by resource. Event receipt must not be the only way an inventory observation becomes current. Per-product subscriptions are required now that subscribeAll has expired. [Subscription constraints](https://developers.cjdropshipping.com/en/api/api2/api/webhook.html#_2-1-subscribe-products-post).
4. Preserve source values, normalized values, units/currency, source endpoint, observed time, and last-success/error state. Unknown money scales or identifiers remain unknown until verified. Supplier-origin changes update supplier snapshots; local merchant-origin values stay local.
5. Derive storefront availability from current eligible source mappings and the local stock/commitment policy. A delisted variant blocks new fulfillment for that source; a cost increase creates a margin/quote exception; neither erases historical orders or silently reprices captured orders.
6. Consequential transitions (fund supplier, cancel fulfilled order, refund customer, mark customer order complete) require canonical domain validation and current provider reconciliation. A valid webhook signature is an authenticity check contingent on the signing key remaining secret, not permission to bypass those rules. Because CJ uses openId as that key and includes it in some payloads, secret custody and provider read-back remain necessary.

## Concrete separation examples

| Event | Correct local result | Incorrect authority transfer |
| --- | --- | --- |
| CJ variant cost rises from USD45 to USD49 after customer accepted retail USD80 | Preserve retail order snapshot; refresh supplier quote/cost and follow funding/margin exception policy | Change buyer charge to USD84 or silently fund the difference from PulseSoc |
| CJ STOCK reports zero | Refresh stock; pause availability for that mapped source if confirmed; preserve merchant copy and history | Delete the merchant product or overwrite own-warehouse inventory |
| CJ order becomes PAID | Update supplier funding observation | Mark the PulseSoc customer payment captured |
| One CJ shipment is delivered while another is pending | Update that shipment/fulfillment; evaluate aggregate local completion rules | Complete the whole customer order directly from a provider status string |
| CJ reimburses a damaged unit after merchant already refunded customer | Record supplier recovery linked to the existing customer refund | Issue a second customer refund |
| CJ product review has score5 | Keep an approved, accurately labeled source review separate if publication rights are established | Insert it into local verified-purchase reviews |

The last example is enforced by the current review-domain design: [create_review](/Users/hmcherie/Desktop/CoinPilotX/services/business_os/marketplace/refunds.py:378) requires the caller to own a completed order containing the product. Any future external-review surface must preserve that meaning.

## Implementation boundary

Business OS and Marketplace call the future normalized Supplier Gateway. The CJ adapter translates source fields, credentials, identifiers, errors and fulfillment operations; it does not own retail pricing, customer-order status, customer money, merchant policy or access-control decisions. Public read/write APIs expose normalized domain objects and capability flags. CJ-specific schema details stay behind the adapter except where a merchant must make an informed supplier choice.

Commercial permission for third-party merchant connections, review/media republication, final account funding responsibility and unresolved API schema units are discovery blockers to settle before implementation. This map establishes ownership even while those provider details remain open.
