# CJ failure recovery matrix

Documentation checked: 2026-09-07. This is a proposed behavior contract only. No retry worker, table, provider request, payment, or UI was implemented. Proposed operational states below supplement the separate supplier fulfillment and customer-payment domains described in [state mapping](CJ_ORDER_STATE_MAPPING.md).

## Global recovery policy

Use merchant/account-scoped queues, bounded exponential backoff with jitter, request deduplication, per-account rate/point budgets, and a durable operation reference. Exact initial delay/retry ceilings are PulseSoc policy and must be configured during implementation; they are not CJ guarantees. Respect explicit server retry hints where returned. Exhausted budget pauses work and exposes a merchant action; it does not create an unbounded retry loop.

Safe reads may retry after transient failures. For create, confirm, pay, cancel, and dispute writes, a timeout leaves an **unknown outcome**. Query the current provider state under the same connection before any replay. No reviewed CJ documentation guarantees exactly-once monetary operations or a general idempotency header. Duplicate-create code1603003 is useful evidence but does not establish replay semantics. [CJ errors](https://developers.cjdropshipping.com/en/api/api2/standard/ps-code.html), [Order lookup](https://developers.cjdropshipping.com/en/api/api2/api/shopping.html#_1-7-query-order-get).

Customer wording below is proposed behavior. Existing customer policy, payment evidence, and service commitments determine actual refunds and notices. Supplier errors must not independently capture, refund, or cancel a customer payment.

Funding limits are local preflight checks, not an atomic CJ spend guard: payBalanceV2 has no expected/max amount field. Fully automatic funding remains gated on CJ confirmation of payId amount-lock and expiry semantics. Webhooks require the documented raw-body HMAC using saved openId, durable receipt and HTTP200 within3seconds; signed callbacks still cannot authorize customer-money changes. See [webhook contract](CJ_WEBHOOK_EVENT_MAP.md) and [supplier contract](PULSESOC_SUPPLIER_CONTRACT.md).

## Additional consequential edge cases

| Case | Required handling |
| --- | --- |
| Duplicate-create error1603003 | Query existing order with the original reference and compare account, lines, address, and amounts; do not issue a new reference just to bypass the duplicate rejection. [Errors](https://developers.cjdropshipping.com/en/api/api2/standard/ps-code.html). |
| Batch detail omits an ID | Missing/foreign IDs are silently skipped; use single lookup when authorized. Do not infer cancellation or deletion from omission. Internal1600000 means retry later. [Batch](https://developers.cjdropshipping.com/en/api/api2/api/shopping.html#_1-16-query-orders-in-batch-post). |
| Cancel requested after CREATED/IN_CART | Regular delete is unsupported; record request, inspect current state, pursue CJ support/eligible dispute, and apply independent customer policy. [Delete](https://developers.cjdropshipping.com/en/api/api2/api/shopping.html#_1-8-order-delete-del). |
| Order status changed during logistics edit8002 | Re-query current order; do not repeatedly submit the old route change. Hard interceptions mean the change did not take effect. [Modify logistics](https://developers.cjdropshipping.com/en/api/api2/api/shopping.html#_1-14-modify-order-logistics-post). |
| Platform-logistics order paid but no waybill | Hold at the actual supplier state with `waybill_required`; ask merchant/operator for the real label through authorized workflow. CJ warehouse awaits the waybill. [Platform flow](https://developers.cjdropshipping.com/en/api/start/Orders-Synchronization-Processing.html#_1-platform-waybill-order-processing). |
| Store Order Flow product unlinked | Order can appear under Imported→Invalid Orders; complete CJ connection before fulfillment. Do not interpret create success as orderability. V3 is explicitly required in this guide. [Store flow](https://developers.cjdropshipping.com/en/api/start/Orders-Synchronization-Processing.html#_3-4-complete-business-process). |
| Dispute create timeout | Keep `businessDisputeId` stable, query dispute list/detail via the mapped order, and reconcile before retry. Unique business ID does not establish a documented idempotent response. [Create](https://developers.cjdropshipping.com/en/api/api2/api/dispute.html#_3-create-dispute-post). |
| Forged/misrouted webhook or external ID | Reject/quarantine malformed data; validate connection ownership and local external mappings; verify state by authenticated provider read before consequential mutation. Do not let an unsigned callback create money or authorize supplier spend. See [webhook event map](CJ_WEBHOOK_EVENT_MAP.md). |
| Quote incomplete | Unknown fee or missing route is not zero. Do not treat `postage` as inclusive of taxes/tariff. Show an estimate only when required components exist; preserve unknown processing time. [Freight Tip](https://developers.cjdropshipping.com/en/api/api2/api/logistic.html#_1-2-freight-calculation-tip-post). |

## Documentation ambiguities that affect recovery

- Authentication prose conflicts on access-token lifetime; use returned expiry timestamps and the shared account's cached token pair. Logout invalidates both tokens, so one store's logout can affect other stores using that same CJ account. [Authentication](https://developers.cjdropshipping.com/en/api/api2/api/auth.html).
- Error1600100 appears as a parameter error in operation examples while the global table uses different meaning. Preserve raw code/message plus operation; do not classify solely by a universal numeric lookup. [Global errors](https://developers.cjdropshipping.com/en/api/api2/standard/ps-code.html), [Shopping examples](https://developers.cjdropshipping.com/en/api/api2/api/shopping.html).
- Exact monetary retry semantics, callback guarantees, processing SLAs, general paid-order cancellation, and refund settlement timing are unresolved. Contract tests and CJ confirmation are prerequisites for enabling dependent automation.
- Proposed operational holds never erase the last verified `supplier_status`; they describe what PulseSoc must resolve next. Customer-money state changes require local payment authority and policy regardless of supplier outcome.
