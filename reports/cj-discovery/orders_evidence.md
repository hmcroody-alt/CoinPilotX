# CJ order, freight, logistics, and dispute evidence

Checked 2026-09-07 against live official CJ documentation. Documentation review only; no authenticated CJ API call, order, payment, credential change, or production mutation was performed. These notes cover the complete published Shopping, Logistic, Dispute, and Orders Synchronization Processing sections, including private inventory, outbound inventory, merge, COGS, and makeup payments. API paths and field names below are technical reference data; examples are not copied as executable requests.

## Principal findings

- **Recommended initial integration, an engineering decision:** CJ catalog identifiers (`orderFlow=1`), `createOrderV2` with explicit `payType=3`, and the documented separate cart → confirmation → parent-payment-order → balance-payment sequence. This makes supplier funding a distinct authorized operation. V3 is required by the synchronization guide for Store Order Flow (`orderFlow=2`), but that guide conflicts with the V2 parameter table. Neither version has a documented general-purpose idempotency header. [V2](https://developers.cjdropshipping.com/en/api/api2/api/shopping.html#_1-1-create-order-v2-post), [V3](https://developers.cjdropshipping.com/en/api/api2/api/shopping.html#_1-2-create-order-v3-post), [Store Order Flow](https://developers.cjdropshipping.com/en/api/start/Orders-Synchronization-Processing.html#_3-2-how-to-use-store-order-flow).
- `payType=1`/omitted on V2 returns a CJ page-payment URL; `2` continues through cart, confirmation, and balance deduction; `3` creates only. V3's request table does **not** list `payType`, although its sandbox description mentions that field. No unsupported V3 automatic-payment behavior should be inferred. [V2](https://developers.cjdropshipping.com/en/api/api2/api/shopping.html#_1-1-create-order-v2-post), [V3](https://developers.cjdropshipping.com/en/api/api2/api/shopping.html#_1-2-create-order-v3-post).
- `storeName` is optional on create. Supplied names must match an API store; omission uses the default API store. Order responses contain `shopId` and a `shopName` snapshot; use `shopId` for association. A named store does not establish a distinct funding account. [Create](https://developers.cjdropshipping.com/en/api/api2/api/shopping.html#_1-1-create-order-v2-post), [Query](https://developers.cjdropshipping.com/en/api/api2/api/shopping.html#_1-7-query-order-get).
- Raw CJ product flow requires a valid CJ `vid` or `sku` and quantity, not a documented Add to My Product prerequisite. Store Order Flow requires V3 according to its dedicated guide, using store identifiers and eventual CJ product connections. Account configuration can enable Store Order Flow even when `orderFlow` is omitted. Confirm that account configuration before implementation. [Flow comparison](https://developers.cjdropshipping.com/en/api/start/Orders-Synchronization-Processing.html#_3-5-comparison-with-cj-product-order-flow).
- Balance funding uses the connected CJ account. No inspected order/payment interface transfers PulseSoc customer proceeds to a merchant's CJ account. A merchant-owned connection requires the merchant to maintain supplier funds or complete CJ page payment. Central credentials would make the central CJ account the account whose funds are used. `1604000` means insufficient balance; `1604001` directs the user to My CJ because balance payment is restricted. [Balance](https://developers.cjdropshipping.com/en/api/api2/api/shopping.html#_2-payment), [Shared payment API](https://developers.cjdropshipping.com/en/api/api2/api/shopping.html#_7-9-balance-payment-v2-post), [Errors](https://developers.cjdropshipping.com/en/api/api2/standard/ps-code.html).

## Reference and money contract

All business API calls below use `CJ-Access-Token`; JSON is the normal body format, except waybill upload/update uses multipart form data. Create V2/V3 additionally describe an optional `platformToken` header whose obtaining process is said to match access-token acquisition; its delegation privileges are not defined in these pages.

| Item | Verified contract |
| --- | --- |
| Create identity | `orderNumber`: required merchant reference, string length 50; V3 describes it as unique. Persist it before sending. |
| Order references | Responses distinguish `orderNumber`, `orderId`, `shipmentOrderId`, later `cjOrderId`, `cjOrderCode`, and `platformOrderId`. Their naming is not interchangeable. |
| Product lines | `products[]`; integer `quantity`; CJ `vid` or CJ `sku` (one required, both must identify the same variant). `storeLineItemId` length 125 correlates local lines; returned `lineItemId` is CJ's line ID. Bundle responses have `subOrderProducts[]`. |
| Address | Required `shippingCountryCode` (two letters), `shippingCountry`, `shippingProvince`, `shippingCity`, `shippingCustomerName`, `shippingAddress`; optional ZIP, phone, county, second line, house number, email, tax/consignee IDs. Carrier rules may make optional schema fields operationally required. |
| Origin and logistics | Required `fromCountryCode` (two letters), `logisticName`. `shopLogisticsType=2` is CJ carrier fulfillment, with no supplied `storageId`; `1` means caller-selected CJ warehouse and caller-supplied waybill; `3` means CJ-assigned warehouse in the create table. |
| Time | `storeOrderTime` is Unix seconds and cannot be in the future. Returned create/payment/store times are documented UTC strings. Private-inventory filters and several auxiliary APIs instead use milliseconds. |
| Monetary output | Product/postage/IOSS/discount/actual-payment amounts are decimal USD; many are specified `(18,2)`. V2/V3 `shopAmount` and `unitPrice` input rows have no explicit currency definition; do not silently assume their denomination or use them as authoritative supplier totals. |
| Taxes | `iossType`: 1 none, 2 merchant IOSS, 3 CJ IOSS; CJ IOSS uses `iossNumber=CJ-IOSS`. The docs describe a €150 CJ-IOSS eligibility boundary; tax compliance and actual applicable charges need separate verification. |

Sources: [Create V2](https://developers.cjdropshipping.com/en/api/api2/api/shopping.html#_1-1-create-order-v2-post), [Create V3](https://developers.cjdropshipping.com/en/api/api2/api/shopping.html#_1-2-create-order-v3-post), [Query order](https://developers.cjdropshipping.com/en/api/api2/api/shopping.html#_1-7-query-order-get), [Freight rules](https://developers.cjdropshipping.com/en/api/api2/api/logistic.html#_1-2-freight-calculation-tip-post).

## Full platform logistics flow

The December 2, 2025 update-announcement link resolves to the current Orders Synchronization Processing page, not a separate new shipping API. The complete documented operational sequence is inventory → warehouse → create → add cart → confirm cart → generate payment parent → pay → upload waybill → optional waybill update while UNSHIPPED. A platform-logistics warehouse does not start its work until the waybill arrives. Ordinary CJ logistics (`shopLogisticsType=2`) omits customer waybill upload and proceeds after payment to order query and tracking query. [Announcement](https://developers.cjdropshipping.com/en/api/introduction.html#update-announcements), [Platform flow](https://developers.cjdropshipping.com/en/api/start/Orders-Synchronization-Processing.html#_1-platform-waybill-order-processing), [CJ logistics flow](https://developers.cjdropshipping.com/en/api/start/Orders-Synchronization-Processing.html#_2-the-process-of-synchronizing-orders-and-utilizing-cj-logistics).

Operational steps are not a newly documented exhaustive logistics-status enum. Order states are in the Shopping state table. `trackInfo.trackingStatus` is a free string with `In transit` only as an example. Keep raw carrier status separately; do not invent a numeric mapping or infer delivery merely from a tracking number. [Order states](https://developers.cjdropshipping.com/en/api/api2/api/shopping.html#order-status), [Tracking](https://developers.cjdropshipping.com/en/api/api2/api/logistic.html#_2-1-get-tracking-information-get).

## Proven limitations and conflicts requiring contract tests/CJ answers

1. V2 table advertises `orderFlow=2`; Store Order Flow explicitly requires V3. V3 has no `payType` field row despite related prose. Confirm account-level defaults and exact side effects of both versions before any monetary test.
2. Platform-flow prose requires warehouse for1/3 and says immutable; V3 table says warehouse selected by CJ for3; changeWarehouse exists, its sample uses localhost, and no precise status gate is stated. Use the published production URL, never its localhost sample.
3. `orderId`, `cjOrderId`, code, parent ID and `shipmentsId` differ across APIs. Store explicit typed references and validate response correlations, including splits/merges and changed IDs for non-CJ variants.
4. Batch-detail status semantics changed on2026-08-19: previously direct PENDING/PROCESSING, now UNSHIPPED plus subStatus. Batch missing/foreign IDs are silently omitted; archived/platform lookup not supported there. Payment-range list max90days, paired filters, excludes unpaid and disallows CANCELLED. List default status is surprisingly documented as CANCELLED: always use explicit filters.
5. `1603003` documents duplicate-create rejection, not replay of the original response or exactly-once semantics. No payment/dispute idempotency guarantee is published. Unknown write outcomes must be reconciled before retry; `businessDisputeId` uniqueness is not sufficient proof of safe blind retries.
6. Delete supports only CREATED/IN_CART; no general paid/shipped ordinary-order cancellation API was found. Update logistics only through editable/cart stage. Dispute and private-outbound cancel endpoints are not substitutes for a paid ordinary-order cancel API.
7. Some freight response rows incorrectly label CNY-named or weight fields as USD. Do not derive currencies/units from inconsistent rows without CJ confirmation; preserve raw values and use unambiguous USD fields. `totalPostageFee` is freight-related, not a guaranteed final all-in retail/customer tax quote.
8. Dispute detail duplicates conflicting date types (string vs milliseconds); list `disputeId` input is integer while detail/create references are strings. Use opaque identifiers and operation-specific validated parsing.
9. No complete logistics free-string status enum, processing SLA, webhook ordering guarantee, return-label API, refund deadline, or return-address workflow is established by these order/logistics/dispute pages.
