# 03 — UNDX VALUE ANALYSIS

**Framing question a buyer will ask:** is UNDX a differentiated agentic platform with real switching cost, or a wrapper around LLM APIs that a competent team rebuilds in a quarter?

**Answer:** neither extreme. UNDX is a **governance layer of genuine quality wrapped around commodity retrieval, with no production execution history.** The valuable part is real and unusual. The parts marketed as its moat — the knowledge corpus and "intelligence" — are not operational.

---

## 1. WHAT WAS MEASURED

**VERIFIED FACT.** Total surface **23,777 LOC**: 5 root modules + 22 `services/undx_*.py` + 12 `services/undx_brain/` modules.

| Module | LOC | Role |
|---|---:|---|
| `undx_execution_kernel.py` | 846 | Proposal diffing, approval-gated writes |
| `undx_brain_layer.py` | 536 | Mission classification, repo file ranking |
| `undx_router.py` | 503 | Multi-provider LLM routing + fallback |
| `undx_worker.py` | 106 | Heartbeat worker (**deployed** — Procfile line 2) |
| `undx_desktop_connector.py` | ~55 KB | File chunking, workspace isolation |

Request path (`undx_router.py:437–502`): message → `route_undx_request()` → `provider_priority()` → provider caller (OpenAI / Claude / Gemini / DeepSeek / Groq) → response with routing metadata. Keys stay server-side; the browser never sees them.

---

## 2. CORPUS DEPTH — **THE HEADLINE NEGATIVE FINDING**

**VERIFIED FACT.** `UNDX_TRAINING/` (372 KB, 13 structured YAML files) and `UNDX_RECON/` (1.0 MB, 18 markdown system maps, dated 2026-08-26) exist on disk.

**They are never loaded at runtime.** A repo-wide grep for `UNDX_TRAINING` and `UNDX_RECON` across all Python returns exactly one hit, and it is a false positive — the policy flag `UNDX_RECONCILIATION_ENABLED` in `undx_mission_runtime.py`. **There is no loader, no import, no reader.**

Further, `UNDX_TRAINING/01_IDENTITY.yaml:1` declares: generated by `scripts/build_undx_training_corpus.py`, do not hand-edit. So the corpus is **auto-derived from the repo, then not used by the repo.**

**Valuation consequence:** corpus contributes **$0** of runtime value. It has modest value as onboarding documentation for an acquirer's engineers — a coherent 1.4 MB system map is genuinely useful in diligence and handover — but it is not a data moat, not training data in any ML sense, and not retrieval material. Any pitch treating it as proprietary AI knowledge is unsupported by the code.

---

## 3. RETRIEVAL — COMMODITY

**VERIFIED FACT.** No vector store. No embeddings. No chunking. No semantic similarity. Retrieval is keyword scoring plus prompt stuffing.

From `undx_brain_layer.py:246–283`:
```
score = 0
for keyword in keywords:
    if keyword in path.lower():   score += 10
    if keyword in content:        score += 3
if path == "bot.py":              score += 4
if path.startswith("pulse_communications_v2/"): score += 8
```

Hardcoded per-path bonuses are the opposite of a generalisable retrieval system. `select_repository_files()` (`:286–319`) ranks by this score and stuffs the winners into context.

**Valuation consequence:** rebuild cost measured in **days**. Contributes negligibly to defensibility. It works adequately for one repo and transfers to no other.

---

## 4. CAPABILITY REGISTRY & AGENTIC ACTIONS — REAL

**VERIFIED FACT.** **98 registered capabilities** in `services/undx_capability_registry.py`.

Read-only majority: list crypto alerts / portfolios / market data / posts / reels / conversations / notifications / relationships; search feed, messages, profiles, content; summarise conversations and comments; translate.

Genuine mutations: pause/resume/create/update/delete crypto alerts; add/remove watchlist items; update portfolio holdings; set post/reel saved state; like/unlike; follow/unfollow; mark notifications read; clear notification categories; update language/timezone/privacy/appearance preferences; delete own posts; send messages.

**Architecturally important:** capabilities live in `PRODUCTION_TOOL_REGISTRY` and are enforced by `undx_tool_gateway.require()` (`services/undx_policy.py:44–48`). A capability absent from the registry **cannot execute regardless of what the model proposes.** This is safety by construction, not output filtering — the correct design, and the thing most teams get wrong.

---

## 5. GOVERNANCE — THE ACTUAL ASSET

**VERIFIED FACT — this is real enforcement, not advisory.**

- **Two-tier approval phrases.** `APPROVE UNDX WRITE` for file writes (`undx_execution_kernel.py:28`); a *separate* `APPROVE UNDX GUARD CHANGE` for changes to the guards themselves (`:80`). Escalating privilege for self-modification is a sophisticated touch.
- **Deterministic policy engine.** `services/undx_agent_policy.py` opens by stating nothing in the module consults a language model. Independent read/write gates (`UNDX_AGENT_READS_ENABLED`, `UNDX_AGENT_WRITES_ENABLED`), kill switches (`UNDX_AGENT_DISABLE_WRITES`, `UNDX_EMERGENCY_KILL_SWITCH`), per-capability allow/deny lists, and an explicit QA user cohort with **no "empty means everyone" fallback** — a classic and dangerous default, correctly avoided.
- **Unconditional risk blocking.** HIGH_RISK capabilities are blocked with no approval override (`:244`).
- **Read-back verification.** 20 verifiers (`services/undx_verification.py:797–820`) re-read state through a *separate* call and compare against requested arguments. States: `verified` / `verification_failed` / `verification_pending` / `impossible_to_verify`. The system refuses to trust a mutation's own success response. This is the single most mature idea in the UNDX codebase.
- **Path blocking.** `.env`, `.git`, venv, secrets, and sqlite paths are refused by the kernel.

**This governance pattern set is genuinely above market.** Most agentic systems ship with prompt-level guardrails and call it safety. This one has registry-gated capability, deterministic server-side policy, kill switches, and post-hoc read-back verification.

---

## 6. PRODUCTION EXECUTION EVIDENCE — **ABSENT**

**VERIFIED FACT.** `undx_execution_log.jsonl`, the audit sink the kernel writes to (`undx_execution_kernel.py:28,715–718`), **does not exist anywhere in the repository or filesystem.**

The only execution log found is `.undx/desktop_connector_log.jsonl`: **246 entries, 2026-05-31 → 2026-07-25**, including real `workspace_register`, `repo_scan`, and `patch_apply` actions. But **every entry targets `.undx_connector_audit_workspace`** — a synthetic sandbox — never the actual repository.

**Conclusion:** UNDX's write path has been genuinely exercised, but only against a throwaway workspace. There is **no evidence UNDX has ever mutated production.** Test coverage is 3 files.

For a buyer this is decisive: the governance is well-designed *in theory*, with no operational track record demonstrating it holds under real load. Design quality without runtime evidence is worth a fraction of design quality with it.

## 7. SWITCHING COST & SEPARABILITY

**Portable (low switching cost):**
- `undx_router.py` — pure provider abstraction, zero PulseSoc coupling. Drops into any system. Also a commodity.
- Governance *patterns* — the ideas transfer even where the code does not.

**Bound to PulseSoc (high switching cost):**
- Tool registry hardcodes PulseSoc routes (`/api/pulse/*`, `/api/crypto/*`, `/api/messages/*`).
- `services/undx_verification.py` alone imports 20+ PulseSoc services (`alert_engine`, `portfolio_service`, `pulsesoc_notification_system`, `feed_intelligence_service`, `social_relationship_service`, …).
- Brain layer keyword tuples are hardcoded to PulseSoc schema.

**INFERENCE:** roughly **40–60% of UNDX is PulseSoc-specific binding.** UNDX is **not separately saleable as a product.** Its value is realised in place, as a feature of PulseSoc, or as a pattern library an acquirer's team studies and reimplements.

---

## 8. HOW MUCH OF PULSESOC CAN UNDX OPERATE?

98 capabilities against a ~1,538-route backend ≈ **6% route coverage**, and the mutating subset is concentrated in low-blast-radius user-preference and social-graph actions. UNDX can adjust a user's alerts, watchlist, follows, saved items and preferences. It **cannot** operate commerce, payments, payouts, ads billing, moderation, or live infrastructure.

**INFERENCE:** UNDX is a competent in-app assistant over a minority of the platform, not an autonomous operator of the business.

---

## 9. UNDX CONTRIBUTION TO PULSESOC VALUATION

**VALUATION ASSUMPTION.** Valued as an embedded contribution to PulseSoc's enterprise value, not standalone (it is not separable — §7).

Positives: 98-capability registry with construction-level enforcement; genuinely above-market governance (two-tier approval, deterministic policy, kill switches, 20 read-back verifiers); deployed worker; keys never client-side.

Negatives: corpus inert; retrieval is keyword matching; **no production execution evidence**; 3 test files; 6% route coverage; not separable; the router is a commodity.

| | Contribution to PulseSoc value |
|---|---:|
| **LOW** | **$15,000** |
| **MID** | **$60,000** |
| **HIGH** | **$180,000** |

**Basis.** MID ≈ 12 person-months of MID-rate rebuild effort (`02_REPLACEMENT_COST_MODEL.md`, domain 6) discounted ~65% for zero production evidence and non-separability, then partially credited back for the governance design being genuinely reusable. HIGH assumes a buyer who specifically wants governed-agent patterns and treats the registry + verification layer as a head start on their own compliance work.

**What would move this materially:** a populated `undx_execution_log.jsonl` showing months of governed production mutations, with verification outcomes, would roughly **triple** the MID figure — because it would convert a design claim into an operational one. That is the cheapest available value-creating action in the entire UNDX surface: turn it on, gated, and let it accumulate an audit trail.
