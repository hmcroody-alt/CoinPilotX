### Entitlements — the complete current file

`mobile-native/ios/PulseSoc/PulseSoc.entitlements` contains **two keys and nothing else**:

| Key | Value | Purpose |
|---|---|---|
| `aps-environment` | `$(PULSESOC_APS_ENVIRONMENT)` | APNs. Build-variable driven, not a literal. |
| `com.apple.developer.associated-domains` | `["applinks:pulsesoc.com"]` | Universal Links. |

`aps-environment` being a build variable is deliberate and load-bearing: a dev-signed build
mints **sandbox** device tokens, and the production deployment does not set
`APNS_USE_SANDBOX`. The resulting `BadDeviceToken` is indistinguishable from a dead token
and gets the token revoked. Do not replace the variable with a literal.

### Associated domains — served AASA

Live at `https://pulsesoc.com/.well-known/apple-app-site-association` (HTTP 200, 1703
bytes), generated by `services/native_app_links.py:78-100`, routed at `bot.py:128713`.

appID: `87ZC69AGSR.com.pulsesoc.app`

| Order | Path | Mode |
|---|---|---|
| 1 | `/pulse` | match |
| 2 | `/pulse/app` | **exclude** |
| 3 | `/pulse/app/*` | **exclude** |
| 4 | `/pulse/*` | match |
| 5 | `/search*` | match |
| 6 | `/dashboard` | match |
| 7 | `/dashboard/*` | match |
| 8 | `/account/*` | match |
| 9 | `/settings/*` | match |
| 10 | `/notifications` | match |
| 11 | `/saved` | match |
| 12 | `/education/*` | match |

**Order is load-bearing and the source file says so.** iOS evaluates components top to
bottom and stops at the first match, so an `exclude` only does anything if it sits *above*
the pattern it carves out of. Rows 2–3 sitting above row 4 is the whole reason the web
client shell stays in Safari. Moving them below `/pulse/*` would be dead configuration that
reads as though it worked.

Also absent from the AASA, both deliberately: `webcredentials` (password autofill
association; prerequisite for passkeys) and `activitycontinuation`.

### Paths NOT claimed, and why that is correct

| Path | Status | Why |
|---|---|---|
| `/open/*` | not claimed, **by design** | Renders an interstitial with an App Store link and a `pulsesoc://` button. Claiming it would break the fallback it exists to provide. |
| `/r/*` | not claimed | Referral links. UA-detects iOS and redirects to the App Store with deferred attribution. See below. |

Both of these get proposed as universal-link paths by people who have not read
`services/app_links.py`. The governing constraint, quoted from that file's header comment:
iOS only hands the app the paths **the shipped binary's AASA claimed**, so a newly-claimed
path does nothing for already-installed users until they update.

### Referral link architecture (relevant to any invite work)

`bot.py:15591` — `GET /r/<referral_code>`:

1. Logs a `referral_events` row (code, referrer, session, landing page, referer, ip_hash).
2. If the visitor is iOS **and** the code resolves to a real user, writes a deferred-claim
   row keyed on `ip_hash` + device-family hash, redeemable within 48h by
   `POST /api/mobile/referral/claim` (`bot.py:15572-15573`) after signup.
3. iOS visitors redirect **straight to the App Store listing** — no landing page, no extra
   tap. Invalid codes still go to the store, just without an attribution row.
4. Everyone else redirects to `/?ref=<code>&utm_source=referral&...`.

This is already an app-first invite path. It solves the case that actually dominates for an
invite — the recipient does *not* have the app — which a universal link cannot solve at
all. Verified in production: `/r/TESTCODE` → HTTP 302.

## Required state, per capability

What each unimplemented capability would add. Portal work means work in the Apple Developer
account that cannot be done from the repo.

| Capability | Entitlement | Info.plist | App Group | Portal work |
|---|---|---|---|---|
| App Attest | `com.apple.developer.devicecheck.appattest-environment` | — | no | enable App Attest on the App ID |
| Live Activities | — | `NSSupportsLiveActivities` | **yes** | new extension App ID + profile |
| App Intents | — | Siri keys if SiriKit | no | enable Siri if SiriKit path |
| Core Spotlight | — | `NSUserActivityTypes` | no | none |

| Share Extension | `com.apple.security.application-groups` | `NSExtension` (own plist) | **yes** | new extension App ID + profile |

| MapKit | — | `NSLocationWhenInUseUsageDescription` | no | none |
| webcredentials | extend associated-domains | — | no | none (server serves it) |

### The shared prerequisite

Four rows above need the same three things — App Group, `keychain-access-groups`, and a
second App ID with its own profile. Build that once as a deliberate foundation (Wave 2 in
the audit), not four times as a side effect.

The keychain point is the one that gets missed. `mobile-native/src/session/sessionStore.ts`
pins the keychain service to `com.pulsesoc.app.session` with **no** access group, so an
extension **cannot read the session token today**. Any widget or share extension showing
personalised content is blocked on that entitlement, and adding it later means migrating
existing keychain items — cheaper to decide up front.

### Expo prebuild considerations

`mobile-native/ios/` is committed, but `app.config.js` runs config plugins
(`withLegacyIosFmtCompatibility`, `withDevelopmentIosIdentity`, plus the Expo plugin set).
Two consequences for extension work:

- Entitlements added by hand to `PulseSoc.entitlements` survive only as long as nobody runs
  a clean prebuild. Entitlement changes belong in `app.json` / a config plugin.
- There is no first-party Expo support for generating extension targets. This needs a
  custom config plugin or a committed-and-defended Xcode project. ~~**Decide which before
  Wave 2 starts** — it is the single largest unknown in the whole plan.~~
  **DECIDED 2026-09-19: committed-and-defended.** `project.pbxproj` is tracked (confirmed
  with `git ls-files --error-unmatch`), `mobile-native/docs/LOCALIZATION.md:403` already
  mandates dual maintenance, and the only prebuild in CI runs in an ephemeral runner and
  asserts nothing about targets. The "defended" half is not optional: a protection test
  pinning target count and names ships with the first extension. Full reasoning in
  `DECISIONS_DEPLOYMENT_TARGET_AND_EXTENSIONS.md`.

Also relevant: `patch-package` runs postinstall and `npm ci` silently drops the patches in
this repo. The current patch set is Hermes + Stripe.
