# Advertiser experience: analytics, diagnostics, recommendations

Modules: `ads_intelligence/diagnostics.py`, `recommendations.py`, `health.py`,
surfaced at `GET /api/business-os/ads-intel/campaigns/<id>/delivery`.

The design goal: an advertiser should never have to ask a human why their
campaign is not delivering, and should never be told something we cannot
substantiate.

## Every cause has an owner

`NOT_DELIVERING_CAUSES` maps each no-fill reason to a headline and an actor —
`ACTOR_ADVERTISER` or `ACTOR_PLATFORM`:

| Cause | Whose problem |
| --- | --- |
| `CAMPAIGN_IN_REVIEW` | Platform |
| `ACCOUNT_UNVERIFIED` | Advertiser |
| `POLICY_BLOCKED` | Advertiser |
| `BUDGET_EXHAUSTED` | Advertiser |
| `WALLET_EMPTY` | Advertiser |
| `SCHEDULE_INACTIVE` | Advertiser |
| `CREATIVE_UNAVAILABLE` | Advertiser |
| `AUDIENCE_MISMATCH` | Advertiser |

Naming the actor is what makes the diagnosis actionable rather than merely
accurate. "Your campaign is in review" tells someone to wait; "your wallet is
empty" tells them to act. Told the wrong one, they do the wrong thing and then
file a ticket.

The mapping is a module-level constant precisely so the diagnostic rules, the
recommendation rules and the tests all read one copy. An inlined second copy
would drift, and the drift presents as a campaign told nothing about why it is
dark.

## Severity

`SEVERITY = {"blocking": 3, "limiting": 2, "efficiency": 1, "informational": 0}`.
`summary_sentence()` renders the highest-severity finding first.

An advertiser reads the first line. Leading with an efficiency tip while the
account is unverified is a correct report that fails at communication.

`MIN_DECISIONS_FOR_DIAGNOSIS = 100` — below that, diagnostics report
insufficient data rather than diagnosing from a handful of opportunities.
`LOW_WIN_RATE = 0.05` and `NOTABLE_INVALID_RATE = 0.05` gate the other findings.

## Recommendations are rules, not predictions

`_RULES` is a 19-entry data table. Each rule has a trigger condition, the
evidence that fired it, and the suggested change.

No recommendation is generated by a model, and none carries a predicted
outcome. We do not say "raising your budget 20% will increase conversions by
15%", because we do not know that, and a confidently wrong prediction spends
somebody's money.

What is said instead: here is what we observe, here is what it usually means,
here is what you might change. The evidence travels with the recommendation so
the advertiser can disagree with our reasoning rather than only with our
conclusion.

## Automation is structurally capped

```python
MONEY_ACTIONS = frozenset({...})   # anything that moves or commits money
max_autonomy_for(action)           # returns LEVEL_RECOMMEND for those, always
```

**There is no `apply()` function in `recommendations.py`.** Not a disabled one,
not one behind a flag — absent. The module can produce advice and has no code
path that enacts it.

`api.py` passes `autonomy_level=LEVEL_RECOMMEND` as a fixed value, not a
parameter, with the reasoning in a comment above it: if a caller could raise the
level, the HTTP surface would become a way to widen what automation may do.

Autonomy levels 0–3 are defined in
[`ads_safety_and_rollout.md`](ads_safety_and_rollout.md). Money actions are
permanently pinned at level 1 regardless of the level configured elsewhere.

## Health and anomalies

`health.py` compares a recent window against a baseline:

| Constant | Value |
| --- | --- |
| `RECENT_HOURS` | 24 |
| `BASELINE_MULTIPLE` | 7 (so a 7-day baseline) |
| `SPEND_SPIKE_RATIO` | 3.0 |
| `DELIVERY_COLLAPSE_RATIO` | 0.33 |
| `CTR_COLLAPSE_RATIO` | 0.40 |
| `MIN_BASELINE_EVENTS` | 200 |
| `MIN_RECENT_EVENTS` | 50 |

Below the minimums, the result is `UNKNOWN`, and `_PENALTY` scores `UNKNOWN` at
**0** — the same as `OK`. Not knowing is not a fault of the advertiser's, and
scoring it as one penalises every new account for being new.

**A new account cannot have an anomaly.** Synthesising a baseline from other
advertisers reports what is unusual for somebody else, which is not a fact about
this campaign.

`_ratio()` returns `None` rather than infinity when the baseline is zero, so a
first-ever day of delivery is not an infinite spike.

Every anomaly carries `"action_taken": "none"` and `"requires_human": True`.
The detector detects. Acting on a spend spike automatically means a detection
bug can halt a legitimate campaign — and the account-level emergency stop, which
*is* an action, is an operator tool in the canonical advertising package, not
something this module can reach.

`_guardrail_factor` reads the canonical guardrail state rather than modelling
account standing a second time, per the one-platform rule in
[`ads_architecture.md`](ads_architecture.md).

## What the advertiser endpoint returns

```json
{
  "ok": true, "campaign_id": "...", "served": 0, "delivering": false,
  "summary": "Your advertising balance is empty. ...",
  "findings": [...], "recommendations": [...],
  "primary": {...}, "degraded": false
}
```

`degraded: true` means we could not read something and the diagnosis is
incomplete — surfaced rather than hidden, because a confident diagnosis built on
a failed query is how an advertiser gets sent to fix the wrong thing.
