# Blue-graphite platform surface audit (Stage 0)

What this is: a complete, mechanical inventory of every near-black colour literal
in the product, each one assigned a role. It exists so that the migration that
follows can be scoped from evidence rather than from a global search-and-replace,
which is the one thing the brief forbids outright.

Nothing here has been migrated. Stage 0 produces the map, not the change.

Generated by:

```
python3 scripts/ui/blue_graphite_color_inventory.py mobile-native/src web static templates services > inv.tsv
python3 scripts/ui/blue_graphite_classify.py inv.tsv --out-csv classified.csv
```

Both scripts are committed. Re-running them is how this document is kept honest;
the counts below are a snapshot and will drift as the codebase moves.

## Why not grep

`grep -r '#000'` answers the wrong question twice. It misses the forms this
codebase actually uses most — `rgba(3, 9, 18, 0.96)`, `#02050b`, `#060d18` — and
it floods the result with text and icon colours, which are the single category
that must *stay* black. So the inventory parses each literal to RGB, keeps only
what is near-black by luminance (perceptual, ceiling 0.16), and records the
CSS/RN property the literal was assigned to. That property is what makes the
difference between a surface and a glyph mechanically visible.

Perceptual luminance rather than WCAG relative luminance is deliberate. The
question here is "would a person call this black?", not "what does this contrast
against". sRGB linearisation pushes every dark value toward zero and flattens the
exact distinction being triaged — `#02050b` against `#363D46`.

### `user_content` — the bucket the first pass got wrong

Without this rule the classifier puts 997 literals in the migration on today's
tree (1,009 when Stage 0 ran; the tree has moved since). 102 are conversation
themes and wallpapers the member selected: nine named chat themes (`pulse_green`,
`deep_space`, `solar_flame`, `royal_purple`, …) and ten named wallpapers
(`galaxy_grid`, `dark_nebula`, `star_tunnel`, …), scoped in CSS by
`[data-control-theme=]` / `[data-control-wallpaper=]` and mirrored in the native
catalog at `mobile-native/src/theme/chatWallpaper.ts`. The ids are persisted
server-side as `appearance.wallpaper`, so both clients agree on them.

They are near-black because that is what the member asked for — one is named
`minimal_black`. Migrating them would not restyle a surface, it would delete a
feature: every chat theme would come out the same colour. Same exclusion as the
user-selectable Black theme, reached from the other direction.

The rule reads the stylesheet's own selectors rather than a list of ids, so a
theme shipped next month is excluded without editing the classifier. The
**default** block carries no attribute selector and stays in scope on purpose: a
member who has chosen nothing is looking at the platform's own chat chrome,
which is what this migration is for.

Three of those buckets are not in the brief's list of ten. They were added
because the repository demands them, and each is a category that would otherwise
have been mis-filed as a migratable surface:

- **`test_pin`** — a test asserting on a literal. Not a surface, but it must be
  edited in the same commit as the surface it pins, or the suite goes red.
- **`documentation`** — a literal quoted inside a comment. This repo argues its
  colour decisions in prose, so the files that reason hardest about near-black
  quote the most of it. Counting those as surfaces inflates the migration with
  text that has no pixels.
- **`non_color_channel`** — `mask-image: linear-gradient(#000, transparent)`.
  The channel being read is alpha; the colour is never seen. Migrating one would
  not restyle a surface, it would punch the wrong hole in one.

## The hard exclusion: real-time audio

**42 literals live in protected real-time-audio paths and must not be touched by
this mission.**


These are named in `config/realtime-audio-protected-paths.json`, and that
manifest names "General UI" as a mission class that must not edit them. The
classifier checks this rule first, before anything else gets a chance to call one
of these a migratable surface. It reads the manifest from the repo rather than
restating the list, so the exclusion cannot drift out of date.

The consequence is worth stating plainly: **the call and live screens will not
match the rest of the platform when this migration lands.** That is the correct
outcome. Closing that gap needs a separate, audio-aware mission with its own
gate run.

## What `static/app/` is, and why it must not be hand-edited

30 literals sit in `static/app/`:

These are **Vite build output** — `static/app/build-source-hash.json` and
`web/vite.config.ts` confirm it. Editing them would be overwritten by the next
web build and would produce a diff that looks like progress and is not.

The source is `web/`, and the scan of it is the most encouraging number in this
document: the entire web SPA source carries **30 near-black literals, 17 of them
structural, and 15 of those 17 are in one file** — `web/src/styles/tokens.css`.

This is also the trap the first pass of this audit fell into: `web/` was not in
the scanned roots, so the generated bundle was inventoried and its source was
not. Any future run must include `web`.

## Rules the classifier applies, in order

Order is the policy. First match wins.

1. **protected real-time-audio path** → `protected_audio`. Outranks everything.
2. **`__tests__/` or `*.test.ts(x)`** → `test_pin`.
3. **inside a comment** → `documentation`.
4. **`mask`, `mask-image`, `-webkit-mask*`** → `non_color_channel`.
5. **a shadow property**, including any custom property whose name contains
   `shadow` → `shadow`. The custom-property arm has to be here rather than with
   the other `--` rules below, because a shadow is written `rgba(0,0,0,.5)` and
   rule 8 would otherwise claim it as a dimming scrim before its name was read.
6. **a text/icon property** (`color`, `tintColor`, `fill`, `stroke`, …) → `text_or_icon`.
7. **a scrim word** in the property or literal (`scrim`, `backdrop`, `dim`,
   `overlay`, `veil`, `shade`, `curtain`) → `dimming_scrim`.
8. **pure black below alpha 0.8** → `dimming_scrim`. A translucent black fill
   with no other role is a scrim in effect even when nothing in the name says so.
   The threshold is strict on purpose: at or above 0.8 the fill is being used as
   a surface, not as a dimmer.
9. **inside a `[data-control-theme=]` / `[data-control-wallpaper=]` block**, or in
   `chatWallpaper.ts` → `user_content`. After rules 5–8 so that a label inside a
   themed block still reports as text: the exclusion is about surfaces the member
   chose, and a glyph is not one.
10. **a file in the `OPAQUE` map** of `backgroundSurfaces.test.ts` → `media_canvas`.
   Parsed from that test, not copied, so adding a screen there starts being
   honoured on the next run with no edit here.
11. **`ThemeContext.tsx`** → `black_theme_requirement`.
12. **a CSS custom property**, classified by the role words in its own name —
    text words checked before surface words, since `--pulse-text-on-panel` is a
    glyph colour.
13. **a known surface property** → `structural_surface`.
14. anything else → `visual_review`.

## The 73 that a script should not decide

This is the honest measure of how much of this audit is still human judgement.
It started at 547 and came down in three steps, each of which is a real finding
rather than a loosened threshold:

| | `visual_review` | why it moved |
| --- | ---: | --- |
| first pass | 547 | line-local parsing; 345 gradient stops had no property |
| + whole-file declaration state | 235 | multi-line CSS declarations now attribute correctly |
| + custom-property naming, masks | 74 | `--bg`/`--panel`/`--glass` resolve by name |
| + user-selected theme scoping | **73** | one themed literal was a review, not a surface |

22 randomly sampled rows from the newly-attributed set were checked by hand and
all 22 were correct.

The remaining 74 split into four groups, and none of them should be decided
mechanically:

**Generated artwork (10).** `ContentCover.tsx`'s `DARK_GRADIENTS` and
`WelcomeUfoOverlay`'s ramps are cover art synthesised for content that has no
thumbnail. A blanket "a colour array is a surface" rule would have filed these as
chrome. They are closer to `media_canvas`.

**User-selectable backgrounds (9).** `static/js/pulse_status_viewer.js` defines
`aurora`, `midnight`, `sunrise`, `emerald` — presets a user picks for their own
status. Restyling them changes user content, not app chrome.

**`<meta name="theme-color">` (6).** One per HTML entry point. These tell the
browser and the OS task switcher what to paint their own chrome. They are not a
surface the app draws, but they must move *with* the page surfaces or the browser
chrome will mismatch the page. Migrate them, but as a deliberate paired change.

**Borders, rings and hairlines (~12), plus a long tail of one-off theme keys.**
`borderTopColor`, `border-left`, `hairline`, `ring`. A near-black border against
a graphite surface may be doing real separation work or may be a leftover from
when the surface behind it was also black. Each needs eyes.

## What Stage 0 does not tell you

- **Whether a `structural_surface` is actually visible.** The inventory finds
  literals, not painted pixels. A surface behind an always-opaque parent is in
  the count and does not matter. Only rendering finds those.
- **Which token each surface should become.** That is Stage 1–2 work, and it
  needs the surface hierarchy (page / panel / raised / inset) that does not exist
  yet as a shared vocabulary.
- **Whether the result passes contrast.** Every migrated surface changes the
  contrast ratio of the text on it. Mission 1 already hit this once: the approved
  card edge `#29466A` had to ship as `#243D5D` because `#29466A` put muted text
  at 3.97:1. Expect more of that, and expect it to constrain the palette rather
  than the other way round.

## Stage 4, and the two things the buckets could not decide

The four heavy stylesheets are migrated. 348 structural literals became 191:
`pulse_status_system.css` 116 → 89, `pulse_messages_v2.css` 92 → 42,
`pulse_desktop_feed.css` 75 → 34, `pulse_home_os.css` 65 → 28. Each commit
carries its own exclusion list, and in each file the total inventory fell by
exactly as much as the structural bucket did — an arithmetic check that is
only satisfiable if no literal quietly changed bucket.

Two decisions came out of the migration rather than out of the audit, and
both are the kind a classifier cannot make because they are about what a
selector is *used on*, not what it is named.

**A control painted on media stays dark, and that decides whole files.**
`pulse_reaction_system.css` is 35 structural literals and is excluded whole.
Its own header calls it shared across "Reels, Statuses, feed", and its four
surface tokens resolve onto selector lists that include
`.reel-action.reel-action-button` and `.pulse-status-action` — controls that
float over a video or a photograph. A graphite pill needs the background
behind it to be dark to read; over a bright frame it washes out. The same
reasoning already excluded the play, sound and reaction controls in
`pulse_desktop_feed.css`, so the file follows them rather than contradicting
them.

That exclusion reached backwards. Four `.pulse-action-button` declarations in
`pulse_desktop_feed.css` had been lifted before the shared language was
traced, and they are the on-card half of the same design vocabulary whose
other half sits on media. The two halves cannot be split without splitting
the stylesheet, so the lift was **reverted**: the action-button language is
now uniformly dark everywhere, which is worth more than half of it being
consistent with the cards around it.

**A selector that appears in two stylesheets must be decided once.**
`.pulse-status-card .status-preview-layer` is declared in both
`pulse_desktop_feed.css` and `pulse_status_system.css` with near-identical
gradients. The first migration moved one and left the other, which would have
put two different fills behind the same element depending on which page you
were on. Reconciled to the migrated value. Worth checking for directly on the
remaining files — a duplicated selector is invisible to a per-file pass, and
the per-file pass is the shape this migration has.

## The native tail, where two of the three files were right already

`ConversationControlCenter.tsx`, `PostCard.tsx` and `HomeScreen.tsx` carried 40
structural literals between them. 13 moved. The other 27 are named below, and
the reason they stayed is the substance of this section: a count of untouched
literals is only reassuring if every one of them is untouched on purpose.

These are also the first consumers of `BLUE_GRAPHITE_LEVELS`. Until now the
native ladder was a constant nothing imported — a declaration of intent with no
enforcement behind it. Importing it instead of restating `#303843` is what makes
a future change to the ladder actually reach the screens. The one place that
still restates the values, `colors.ts`, documents why: two gates parse that
object by regex and would silently drop keys.

**`ConversationControlCenter.tsx` — 10 of 11.** The native twin of the web
control centre, so the role assignments were already decided in
`pulse_messages_v2.css` and only had to be repeated: the sheet is `panel`, the
bands on it (`header`, `sectionHeader`) are `raised`, the cards in it
(`dashboardMetric`, `detailPanel`) are `raised`, and every control chip and text
field (`gear`, `headerButton`, `close`, `sectionIcon`, `searchWrap`) is `inset`.
The survivor is `notice` at `#0e2b31`, a dark teal banner that prints
`colors.accent` on itself. That is an accent-tinted state surface, the same
category as the gradient tails preserved in stage 1, and lifting it to graphite
would delete the tint that carries the meaning while changing a measured
contrast pair for no reason.

**`PostCard.tsx` — 3 of 11.** The on-media test decided this file almost
entirely. `mediaTilePlayBadge`, `mediaVideoMute` and `mediaMore` sit on
photographs and video; `liveStage` is a video canvas and `liveProcessing`,
`liveProcessingBadge`, `liveProcessingShade` and `liveStageButton` are the
livestream surfaces around it, which this mission is not allowed to touch at
all. That leaves three surfaces that are card chrome and nothing else — the
overflow sheet (`panel`, matched deliberately to the control centre's sheet so
the platform has one bottom-sheet colour), the reaction toolbar (`panel`) and
the inline comment composer (`inset`, because it is a text well).

**`HomeScreen.tsx` — 0 of 18, and that is the finding.** Fifteen of the
eighteen are tints at **0.03 alpha**. Substituting the hue of a 3% wash changes
the composited result by about one unit per channel, so migrating them would
have produced a diff with no pixels behind it. Worse than useless, in fact:
`hero`, `heroTile`, `heroMetricCell`, `heroMetricBlock` and `heroHealthPill` are
painted *on top of* the blue-graphite material that mission 1 already installed,
and the only job a 3% tint has there is to be a whisper of separation from the
base beneath it. Replacing its hue with the base's own hue nulls the whisper.
The tint is doing the opposite of what a near-black literal usually means.

Of the remaining three, `actionErrorBanner` is `rgba(74, 24, 24, 0.92)` — dark
**red**, a danger surface that the inventory catches only because it is dark.
`drawerOverlay` and `heroMapPanel` are declared and never referenced; they are
dead style keys, and migrating dead code is how a migration inflates its own
numbers. Three of the fifteen tints are Pulse Radio (`commandRadioNow`,
`commandRadioPanel`, `heroRadioPill`) and two are frozen city-scene art
(`heroPlanetShadow`, `heroSkylineTower`), both already excluded on the web side,
so the two platforms agree without having been coordinated.
