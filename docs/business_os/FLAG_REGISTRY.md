# Business OS v2 — Feature flag registry

Tiers 0.1 through 0.5 added seven new build-time flags and left nothing that
lists them together. This document is the inventory: every `EXPO_PUBLIC_*`
variable the mobile app reads, the module that reads it, the accessor that
answers for it, what turns on when it is set, and which mission or tier put it
there.

Three defects this registry named have since been fixed, and the entries below
describe the code as it stands after them: the four parsing rules are now one
shared reader, the two tautological MOCK-DATA locks are real locks, and the one
flag with no call sites has been deleted rather than left saying something
untrue.

It is generated by reading the code rather than by reading the earlier
completion reports. Where a report and the source disagree, the source is
recorded here and the disagreement is named.

## How a flag is read

There is one reader: `envFlagOn` in **`src/core/envFlag.ts`**. It accepts

```
1   true   on   yes
```

case-insensitively and after trimming surrounding whitespace. Everything else —
`0`, `false`, `off`, an empty string, and an unset variable — is off. Every
boolean `EXPO_PUBLIC_*` gate in the app goes through it, including the two
app-level constants in `api/config.ts`, the QA flags and the perf overlay.
`src/core/__tests__/envFlag.test.ts` pins the accepted set, runs it through
every accessor, and reads the source to fail if a new flag reinvents the rule.

### What this replaced

Until this fix there was no flags module at all, and each surface wrote its own
parser inline. Six rules were in use:

| Parser | Accepted | Trimmed | Used by |
| --- | --- | --- | --- |
| `flagOn` in `api/commerceInbox.ts`, `api/eventsManager.ts` | `1`, `true`, `on`, `yes` | no | the Messages flags, the three Events flags |
| `envFlag` in `api/paymentsHub.ts`; inline in `api/ordersDashboard.ts`; `adsPostModeEnabled` | `1`, `true`, `on`, `yes` | yes | the six Payments flags, both Orders flags, `ADS_POST_MODE` |
| `=== "1"` after `.trim()` | `1` only | yes | all six Tier 0.5 flags |
| `=== "1"` with no trim | `1` only | no | `DIGITAL_COMMERCE_ENABLED`, `NATIVE_CALLKIT_ENABLED`, the QA flags |
| lowercase, no trim | `1`, `true`, `on`, `yes` | no | `conversationSplitEnabled` — accepted `true`, rejected `" 1"` |
| `["1","true","on"]` after trim + lowercase | `1`, `true`, `on` | yes | the perf overlay in `App.tsx` — the only one that rejected `yes` |

The consequence was not cosmetic. `EXPO_PUBLIC_ORDERS_ESCROW=true` turned escrow
on; `EXPO_PUBLIC_STORE_READINESS=true` did nothing at all, and nothing said so at
the point where an operator sets the variable. Flags shipped in adjacent tiers
disagreed about what "on" meant, which is the shape of a "we turned it on and
nothing happened" report. Both spellings now work, on every flag.

The migration widened what counts as *on*; it did not touch what happens when
nobody sets anything. Every flag below still defaults off.

One flag needed care and kept its shape exactly: the QA kill switch
`EXPO_PUBLIC_PULSESOC_DISABLE_TEMP_QA_ACCOUNT` is still inverted and still the
last term of an `&&` chain fenced by a loopback base URL — it reads
`!envFlagOn(...)`. Spelling a kill switch `true` used to fail open; it does not
now. The perf overlay is still short-circuited by `__DEV__`, so the flag still
only answers for Release and QA builds.

## Flags that default on

**None of the twenty-six feature flags defaults on.** Every accessor goes
through `envFlagOn`, so an unset
variable resolves to `false` and the gated surface is absent. That is the
correct posture and it is worth stating plainly, because the earlier missions
each asserted it locally and no document had ever checked all of them at once.

Two things come close enough to record.

`EXPO_PUBLIC_PULSESOC_DISABLE_TEMP_QA_ACCOUNT` is the one flag with inverted
polarity. `session/qaTemporaryAccount.ts` reads it as `!envFlagOn(...)`, so the
permissive side is the default. It is safe only because it is the third
condition in an `&&` chain whose first two terms are a localhost API base URL
and two other QA flags that both default off. The composite gate defaults off;
the individual flag does not. If either of the other two conditions is ever
relaxed, this one stops being harmless.

`EXPO_PUBLIC_PULSESOC_PERF_OVERLAY` is short-circuited by `__DEV__` in
`App.tsx`, so perf tracing and the on-device overlay are on by default in
every development build regardless of the environment. The flag exists to turn
the same thing on in Release/QA builds. This is intended — `components/PerfOverlay.tsx`
says so — but it means "defaults off" is only true of production builds.

## Flags read in more than one place

Only one boolean gate is read at more than one site, and the two sites agree:
`marketplaceLocationHonestyEnabled()` is called at `MarketplaceManagerScreen.tsx:194`
and again at `:1267`. Both calls go through the same accessor, so there is no
fallback to diverge.

The genuine multi-reader hazards are the two non-boolean variables:

`EXPO_PUBLIC_PULSE_API_BASE_URL` is read in `src/api/config.ts:7` and again in
`app.config.js:18`. Both fall back to `extra.pulseApiBaseUrl` and then to
`https://pulsesoc.com`, but only the runtime read normalises the result
(`normalizeApiBaseUrl` strips trailing slashes and rejects anything without an
`http(s)` scheme, silently substituting the production host). A malformed value
therefore lands in `expoConfig.extra` unmodified and is corrected only on the
way out. The two never disagree today; they could.

`EXPO_PUBLIC_EXPO_PROJECT_ID` is read in `src/api/config.ts:35` and
`app.config.js:19`, with different fallback chains — the runtime read tries
`easConfig.projectId` before `extra.expoProjectId`, the config read tries only
`extra`. Two sources of truth for one identifier.

Every other flag has exactly one read site behind exactly one exported
accessor, which is the pattern the rest of this registry assumes.

### `EXPO_PUBLIC_MESSAGES_REALTIME` — deleted, and why deletion was the honest option

`messagesRealtimeReorderEnabled` was exported from `api/commerceInbox.ts` and
imported by nothing. A repo-wide search found the definition and no call site,
so setting the variable changed nothing anywhere in the app. The audit left the
question open: was the animation never wired, or wired unconditionally?

Reading the screen answers it. `CommerceInboxScreen`'s live-update effect
upserts a touched conversation to the top of the list on every cache write, and
that reorder is **unconditional** — it has always run, in every build. What does
not exist is motion: there is no `LayoutAnimation`, no transition, nothing
animated anywhere in that path. So the flag named a real behaviour that ships on,
and claimed to gate an animation that was never built.

Neither wiring survives scrutiny. Gating the *reorder* would take a behaviour
that works today and switch it off in every default build — a regression dressed
as a fix, and forbidden outright by the rule that this pass changes no flag's
effective behaviour. Gating an *animation* means writing the animation first,
which is a feature, not a defect fix, and not something to add under cover of an
audit.

That leaves deletion. The accessor and the variable are gone; the reorder is
unchanged and is now documented as unconditional in the screen's own header,
where a stale comment had claimed it was flag-gated. `MESSAGES_COMMERCE_INBOX_REPORT.md`
still describes the flag as gating the animation; it is a historical completion
report and has been left as written, but it is wrong on this point and this
registry is the current record.

`PAYMENTS_MOCK_DATA_GAPS` records a related non-flag item worth repeating here:
there is no re-authentication primitive anywhere in this app, so nothing can be
gated behind step-up auth. Every action that would need it is currently absent
for other reasons. That has to be built before any of these six flags is turned
on.

## Areas with no flag

Two of the eleven Business OS surfaces have no `EXPO_PUBLIC_*` gate of their
own, which is worth recording so nobody goes looking for one.

**Verification** has none. Tier 0.3 rewrote the status logic and the copy
unflagged, which means — unlike Store readiness and Marketplace location — the
Verification repair is live in the default build.

**The Hub** has none either. Its switch is `HUB_LIVE_CARDS` in
`api/businessOs.ts:117`, a hard-coded `export const HUB_LIVE_CARDS = false`.
It is not an environment variable and cannot be turned on without a code
change, which is the state the hub revert deliberately left it in.

Three further hard-coded `false` constants gate Marketplace surfaces the same
way — `MARKETPLACE_OFFERS_ENABLED`, `MARKETPLACE_CART_ENABLED` and
`MARKETPLACE_BOOST_ENABLED`, all in `api/marketplaceOffers.ts:80–103`. Several
MOCK-DATA rows name these as their gate. They read like flags in the gap tables
and are not flags; changing one is a commit, not a build variable.

## Summary

Twenty-six feature flags. Every one defaults off in a production build. One QA
flag has inverted polarity and one developer flag defaults on in `__DEV__`.

The twenty-seventh was `EXPO_PUBLIC_MESSAGES_REALTIME`, which gated nothing and
has been deleted. All twenty-six now read one shared parser — the six that
arrived with Tiers 0.4 and 0.5 used a stricter rule than everything before them,
which was the single most likely source of a "we turned it on and nothing
happened" report, and is no longer possible: `src/core/__tests__/envFlag.test.ts`
runs the same four values through every accessor and reads the source to catch a
new flag that invents its own rule.

The pattern worth flagging to the product owner is not any individual entry.
It is that four of the Tier 0.5 corrections the verdict record classifies as
DEVIATIONS — the store-open claim, the "near you" claim, the em dash, the
double-counted badge — all shipped behind flags that are off. The defects the
tier was raised to fix are still what a default build renders. Whether that was
the intent, or whether these flags were meant to be flipped on before release,
needs owner confirmation.
