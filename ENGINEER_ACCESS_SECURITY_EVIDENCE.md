# Engineer Access Gate — Security Evidence Record

Mission: Engineer Access Gate for Galactic Construction. Owner: Roody Cherie.
Recorded: 2026-08-05. Branch: `codex/emergency-live-audio-recovery`.

This document is the §14 "tests and security evidence are recorded" artifact. It states
what was built, what was proven mechanically, and what remains open and can only be closed
on hardware.

## Architecture summary

Authorization is a server decision. The client holds no rule that can grant access. The
passcode is one of four independent conditions, and the server evaluates all of them:
a valid authenticated PulseSoc session, the immutable owner account ID or a server-issued
engineer role, the correct passcode compared against a PBKDF2-HMAC-SHA256 hash held in an
environment variable, and the absence of an active lockout. Only when all four hold does the
server mint a short-lived HMAC-signed capability token naming the account, the session, the
expiry, and the allowed scope.

The policy itself lives in `services/business_os/engineer_access.py`, deliberately free of
Flask, of the database, and of any `bot` import, so that it can be exercised in isolation and
so that no request-handling detail can quietly become part of an authorization decision.
`bot.py` exposes it at `POST /api/internal/engineer-access/verify` and
`GET /api/internal/engineer-access/session`.

The passcode value never appears in the repository. It exists only as a PBKDF2 hash in a
deployment environment variable, generated by `scripts/generate_engineer_access_hash.py`.

## Evidence produced

The backend policy suite in `tests/business_os/test_engineer_access.py` runs 76 tests and all
76 pass. The tests deliberately use a different passcode from the production value, and an
autouse fixture strips all four engineer-access environment variables so no test can read real
deployment configuration.

Four results in that suite carry most of the security weight. First, denial uniformity: seven
distinct causes of refusal — wrong passcode, unknown account, unapproved role, suspended
admin, disabled feature, missing configuration, malformed input — are serialized and collected
into a set, and that set has exactly one member. The denial payload is byte-identical
regardless of which check failed, mentions none of the words that would narrow it down, and
never echoes the submitted value. Second, timing: `evaluate_engineer_access` computes the
identity result and the passcode result before it branches, so the key-derivation cost is paid
on every path and cannot be used as an oracle for whether an account is authorized. Third,
brute force: a sweep of one thousand wrong passcodes against a correctly configured owner
account grants nothing on any iteration. Fourth, grant integrity: tokens are rejected when the
payload is tampered with, when signed by the wrong secret, when expired, when replayed after a
newer grant has been issued, when presented by a different account, and when presented under a
different session.

The §9 prohibition on authorizing by mutable profile data is enforced structurally rather than
behaviorally. One test inspects the signature of `engineer_identity_authorized` and asserts
that no parameter is named email, username, display name, name, profile, avatar, or handle. A
second passes an impostor user object with every one of those fields set favorably, plus
`is_owner`, `is_admin`, `role`, `engineer`, and `developer_mode`, and asserts it is refused. A
future edit cannot start honoring an editable field without one of these failing.

The §6 session-lifetime rule is enforced the same way. Rather than testing each sign-out
helper, the tests target `stateFor`, the single AuthState constructor every auth transition
funnels through, and add a source assertion that at least five constructors still route through
it and that both `reconcileEngineerAccessOwner` and `clearEngineerAccess` remain present in
`auth.ts`. A hand-rolled sign-out path that bypasses the constructor fails that assertion.

Leak containment was checked directly. A repository-wide grep for the passcode across Python,
TypeScript, JavaScript, JSON, and Markdown returns no matches. The client grant store asserts
against its own source that it imports neither AsyncStorage, SecureStore, expo-secure-store,
nor any analytics or tracking call — a stronger guarantee than asserting those calls are never
made. The modal test serializes the entire rendered tree and asserts the passcode does not
appear in it, and asserts the field is cleared before the network call resolves rather than
after.

The client-side owner allowlist that previously existed in `businessConstruction.ts` was
removed. Its test file is now a regression guard asserting that the export is gone, that no
email-shaped string appears anywhere in the module source, and that the default access shape
grants nothing.

Finally, the realtime-audio change gate was run and is unaffected by this mission. The paths it
flags are pre-existing work on the current branch; none is a file this mission touched.

## Open items

Two categories remain, both requiring a machine this work was not performed on.

`npm run verify` — typecheck, i18n validation, and Jest — has not been executed. The sandbox
this work was authored in terminates any process exceeding roughly forty-five seconds and does
not persist background processes between calls, and neither `tsc` nor a cold `jest` run fits
inside that budget. What was verified instead: every file listed above parses cleanly as
TypeScript/TSX under the project's own Babel parser, and every named import in every new test
file resolves to a real export in its target module. That rules out syntax errors and
missing-export errors but not type errors, and it does not execute a single assertion. The
frontend suites should be treated as unrun until `npm run verify` passes locally.

Physical-device QA per §13 and §14 has not been performed: Face ID device, small and large
iPhones, large Dynamic Type, Reduce Motion, offline and weak network, logout and account
switching, and both the Business and Marketplace entry points. Access being verified on a
physical iPhone is a stated completion criterion and remains outstanding.

Three smaller spec items are also not yet implemented: the §11 thin cyan/purple energy sweep on
success (only the lock-to-unlock icon change exists), the §6 optional Face ID re-lock when the
app returns from the background before reopening sensitive routes, and passing `session_id` in
the verify request body — the endpoint accepts it, but the client currently sends only the
passcode and the device ID.
